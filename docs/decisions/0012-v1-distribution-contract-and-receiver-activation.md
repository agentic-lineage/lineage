# 0012 V1 Distribution Contract And Receiver Activation

Status: Accepted — the core loop (publish, storage, pull, enable) is built, deployed, and has been exercised end to end against the real production registry, not just tests. See "Verified in production" below.

Date: 2026-08-20

Updated: 2026-08-26 — production registry storage moved from GitHub Releases
to Supabase Postgres plus a private Supabase Storage bucket. The public website
API, GitHub publisher identity, package ownership rules, and receiver CLI
contract remain unchanged.

## Context

The `Goal: Enable distribution` milestone (#67-#77) is the current blocker: it's what turns Lineage from "clone the repo and run it yourself" into something a real author and a real non-coder receiver can use end to end, which is a precondition for any V1 launch. Packaging (`package init` / `validate` / `export`) already works and is out of scope here.

Three open `needs:decision` questions were blocking everything downstream of them: where published packages actually live (#67, #69), how the `lineage` CLI itself gets installed (#64), and what the primary receiver activation experience is, especially for people who will never type a CLI command (#77).

An earlier version of this decision proposed a custom backend with its own blob storage and metadata database. That was revised before the V1 loop shipped: GitHub Releases provided a fast bootstrap registry, with versioned asset hosting and access control through a private repo. After the first real package was published and the website registry API existed, the active production storage moved to Supabase so Lineage can keep queryable metadata, aggregate metrics, and package archives in one operator-controlled place without changing the CLI/public API contract.

## Decision

1. **Hosting/storage.** Active production package metadata lives in Supabase Postgres, and package archives live in a private Supabase Storage bucket behind the website API. The previous shared private GitHub Releases repo, [`agentic-lineage/published-artifacts`](https://github.com/agentic-lineage/published-artifacts), remains the migration source and rollback path for the initial packages, but GitHub Releases are no longer the active registry store.

2. **Website's role.** The existing `landing/` Vercel deployment is the registry boundary and storage adapter host. Publishers authenticate to the website's publish API with a GitHub-issued bearer token; the website verifies that token with `GET https://api.github.com/user`, records the verified login as owner, writes metadata/metrics to Supabase Postgres, and writes immutable archive bytes to private Supabase Storage. Receivers (CLI pull, `lineage add`, and the bootstrap prompt) call the website's read API, which resolves metadata and proxies the private archive bytes — no receiver needs Supabase or GitHub credentials. `landing/` remains the "Lineage website" referenced by #69, rather than a new `website/` directory or a separate codebase.

3. **Versioning.** Version identity is **not** tied directly to any storage provider. It's the package's own manifest-declared version (`lineage.yaml`) plus the content digest, matching 0005 (manifest is authoritative, digest is the integrity check). Supabase rows use `<package-name>, <version>` as the immutable key and store the digest alongside the archive path. The CLI always verifies against the manifest version and digest, never trusts a storage path or row alone as version of record. This is the same portable package/version model the GitHub-backed V1 used.

4. **CLI install mechanism — superseded.** This originally proposed `npx @lineage/cli` as the V1 install path, deferring prebuilt binaries. That was superseded before the npx wrapper was ever built: `npx` still requires Node, and the actual goal (anyone can get the CLI, no toolchain assumed) is better served by a real installer. Shipped instead: `curl -fsSL https://agenticlineage.vercel.app/install.sh | sh` — detects OS/arch, downloads a prebuilt binary (macOS/Linux, amd64/arm64) from the `lineage-code` GitHub release, verifies it against the release's `checksums.txt`, and installs to `~/.lineage/bin`. Windows gets a direct `.exe` download link. `go install github.com/agentic-lineage/lineage/cmd/lineage@latest` works too, for people who already have Go. A non-coder receiver never needs to know either of these commands exists; the bootstrap prompt (below) runs the installer on their behalf. The npx path (#7) is no longer planned - the curl installer covers the same need with less to build and maintain.

5. **Receiver activation, primary path.** The primary documented flow (README, website) is a short, copy-pasteable instruction block that a non-coder pastes into their coding agent's chat (Claude, Codex, etc.). The agent uses its own shell access to: run the curl installer (decision 4), fetch the referenced package, inspect/validate it, walk through permission-gated setup, and enable it — leaving the user with an active, ready-to-run workflow and the exact command to spawn/run it next. `lineage add <package-ref>` (#77) is the direct CLI command underlying this flow and stays documented as the path for people who already have Lineage installed. The prompt text itself lives at `docs/bootstrap-prompt.md`, versioned alongside the CLI (#98), and has now been tested against both a benign package and an adversarial package with injection attempts in package-controlled content.

6. **Publisher identity and package ownership.** Superseded by decision 6b below — kept here for history. The first version of this decision used a flat, admin-minted `LINEAGE_PUBLISH_TOKENS` mapping (`token:publisher-id` pairs), which meant every new publisher required a manual env var edit and a redeploy. That doesn't grow.

6b. **Publisher identity is a verified GitHub login, not an admin-minted token.** Publisher identity stays on GitHub even though active package storage moved to Supabase: `lineage login` runs GitHub's OAuth Device Flow (the same mechanism `gh auth login` uses — no client secret required, safe for a public/native CLI), scoped to `read:user` only, and stores the resulting GitHub access token locally. `lineage package publish` sends that token as the request's bearer token; the website verifies it by calling `GET https://api.github.com/user` and uses the verified `login` it gets back as the publisher id — never a client-supplied string. Ownership works exactly as before (first publish of a name claims it for that login; a later publish from a different verified login is rejected, 403), but now adding a publisher requires zero action from the site operator: anyone with a GitHub account can `lineage login` and publish. Publish is **open** — any verified GitHub account can publish a new package name — matching how npm/crates.io/PyPI work, rather than gating behind a pre-approved list. `LINEAGE_PUBLISH_TOKEN` remains as an escape hatch for non-interactive use (CI): set it to any GitHub-issued token with `read:user` access and the website verifies it exactly the same way, no separate CI-specific mechanism needed.

7. **Publish is interruption-safe.** Publish is commonly agent-driven — an agent shells out to `lineage package publish` on the author's behalf — and that agent's own session/usage can end mid-command, same as a network drop or a serverless function timeout. In the Supabase-backed registry, the website validates request identity and package ownership first, writes the archive bytes to private storage, then commits the metadata row and publish metric. A version never becomes visible before its archive exists. Retrying the identical publish returns idempotent success when the same `name@version` already exists with the same digest, and returns conflict if the digest differs. The original GitHub-backed registry used draft Releases for the same recovery property.

8. **Every package gets a real, shareable link.** `/packages` on the website lists the latest visible version for each package name through the paginated registry API; `/packages/<name>` is a dedicated page per package (name, version, description, publisher linked to their GitHub, digest, aggregate metrics, the exact `lineage package pull <name>` command, and a direct archive download), with proper OpenGraph/Twitter metadata so pasting the link into Slack or Twitter shows a real preview instead of the generic site card. Download, resolve, search, view, and publish counts are aggregate registry events; public UI exposes counts only, not per-user browsing identity.

## Consequences

- Publish (#68) needs an authenticated upload path against the website's publish API instead of a raw `git push`; the website does the actual GitHub Release creation server-side. Identity comes from GitHub's own OAuth device flow (decision 6b), so the website never mints or stores publisher credentials itself — it only ever verifies a token GitHub already issued.
- `lineage login`/`lineage logout` are new CLI surface, and publish's failure mode when nobody's logged in (and `LINEAGE_PUBLISH_TOKEN` isn't set) needs to say so clearly rather than a bare 401 from the website.
- Pull (#70) and unified artifact processing (#71) resolve package refs against the website's read API, which resolves `<package-name>@<version>` to a registry metadata row and private archive object. Digest verification stays the CLI's job regardless of transport — website/API metadata is advisory, the package digest is authoritative (already an acceptance criterion on #67).
- Rate limits now live at the website API boundary for list, resolve, download, and publish routes. The initial GitHub-backed registry inherited GitHub Releases API limits; Supabase removes that shared GitHub token bottleneck for normal read/download traffic while still depending on GitHub for publisher identity verification.
- The bootstrap prompt is a content artifact, not just a command: it needs to be written, versioned alongside the CLI, and reviewed for prompt-injection safety, since it's pasted into an agent that has real tool access on the receiver's machine.
- Provisioning now includes Supabase Postgres, a private Supabase Storage bucket, and server-side website secrets for `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_STORAGE_BUCKET`, and `LINEAGE_REGISTRY_STORAGE=supabase`. The GitHub registry token/repo remain useful for rollback and backfill, but are no longer the active package storage dependency.
- `lineage add` (#77), `pull` (#70), and the bootstrap prompt are meant to converge on the same validate → inspect → permission-gated setup → enable state machine (#71) rather than each getting a separate code path - `pull` exists today, the shared machine itself doesn't yet (see Follow-Up).
- The original GitHub-backed registry could leave abandoned draft Releases after interrupted publishes. The Supabase-backed registry avoids making a version visible until archive storage and metadata commit succeed, so stale private objects are the cleanup concern instead of public/draft release clutter.
- GitHub's Releases API refuses to finalize (un-draft) a release in a completely empty repository (`"Repository is empty."`, 422) — a repo with zero commits has no default branch for a release to resolve against. `published-artifacts` needed one throwaway commit (a README explaining the repo is Releases-only) before the very first publish could finalize. Worth remembering if the registry repo is ever recreated.
- `go.mod`'s module path (`github.com/lineage-dev/lineage`) pointed at a GitHub org that never existed — `go install`/`go get` silently could not work for anyone, ever, until this was caught and fixed (module renamed to `github.com/agentic-lineage/lineage`). A tagged release built before the fix (`v0.2.0`) still carries the broken path; `go install ...@latest` only resolves correctly from `v0.2.1` onward. The public Go module proxy also caches `@latest` resolution independently of GitHub and can lag a tagged release by some (unpredictable) amount of time - `GOPROXY=direct` bypasses that cache for verification.

## Verified In Production

Not just tested in isolation - the full loop has actually been run against the real, deployed registry:

- Real `lineage login` completed end to end: a human approved the device code in a browser, `lineage whoami` correctly reported the resulting GitHub identity.
- Two real packages published with that identity, via two different paths: directly via CLI flags (`lineage package publish ./examples/resume-workflow`), and by writing a short natural-language instruction ("create a package that does X, then publish it") and following it as if it were a prompt handed to a fresh agent, rather than typing flags directly - a smaller-scale rehearsal of what the eventual bootstrap prompt (decision 5, #8) will need to do.
- Both are live on `GET /api/packages` and have working `/packages/<name>` pages with correct publisher attribution.
- A third machine (a clean receiver `LINEAGE_HOME`) pulled a published package by name, verified its digest matched what the registry reported, enabled it in a fresh project, and produced a correct `lineage run claude --dry-run` launch plan naming its skills and workflow.
- The curl installer (decision 4) was run twice against the live release, from a clean environment each time, using the exact command shown in the hero - not a local file.
- The registry backend was migrated to Supabase on 2026-08-26 and verified against production: `/api/packages` resolves `ai-product-engineer-resume@0.1.2` as latest, `/api/packages/ai-product-engineer-resume` returns the expected digest/publisher/metrics, and `/api/packages/ai-product-engineer-resume@0.1.2/download` serves the archive successfully through the website proxy.
- The Supabase migration rehearsal included local registry unit tests, CLI publish/pull end-to-end coverage, Playwright coverage for the registry browsing flow on desktop and mobile, and a protected Vercel Preview test of publish/list/resolve/download/idempotent republish before the production switch was set.
